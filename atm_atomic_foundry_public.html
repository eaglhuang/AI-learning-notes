AI 裸奔時代的終結：幫你的多 AI 加速開發同時加裝安全煞車

當 N 個 Agent 同時變更同一個 Repo，如何進駐「原子鑄造廠」，以 5D CID 鍛造穩固的系統治理基石

把整個 repo 想像成一座鑄造廠。每段被 AI 寫出來的程式都會領到一張多維身分證（5D CID）、一份可被半年後重放的 SHA256 證據包、一條從 ORIENT 走到 CLOSURE 的七階生命週期。鑄出來的不是匿名 diff，是有名字、有合約、可被審計與重用的細胞。煞車不是讓你慢下來，而是讓你同時開五個 Agent 也不會把專案撞爛。

1. 多 AI 同時開發一個專案會撞到的牆

第三十天你會發現，看著三個 Agent 同時改你的 repo，比自己一個人寫還累。

剛開始用單一 AI 助手寫程式，體驗會非常爽。它幫你補檔、補測試、補 README，你不用打字也能進度神速。然後你開始多開幾個 AI：Claude Code 處理一張卡、Codex 跑另一張、Copilot 在 IDE 裡開第三條 PR。你以為效率會三倍，結果撞到三面牆。

第一面牆是重複造輪。Agent A 寫了一個 HTTP retry helper，三週後 Agent B 在另一個 feature 又寫了一個幾乎一樣的，再過兩週 Agent C 又寫了第三個。沒有人在看「這段語意上已經存在了」，因為每個 Agent 都只看到自己當下的上下文。

第二面牆是 scope 互踩。三個 Agent 同時改一個 repo，沒有一個機制告訴它們「這個檔案有人正在動」、「這個權限這輪只能給一個人」。等到 git merge 才發現衝突，太晚了。

第三面牆是結構慢性衰敗。每個 feature 都做對了，半年後檔案卻越來越肥，tasks.ts 從 300 行漲到 1500 行，沒有人在看「這個檔案該拆了」、「這 30 個原子裡有 12 個語意重複」。每個局部都對，整體在悄悄崩壞。這是結構熵，從來不會在某一個 PR 裡跳出來，它是時間累積出來的慢性病。

第四面牆最隱蔽——沒有身分。不論你寫的多漂亮，每一段 AI 寫出來的程式碼都是匿名的字串，它只活在那一個專案的 git history 裡。如果隔壁專案的某個 helper 跟它語意上完全一樣，它們不知道彼此存在，下一個新專案也認不出它們。每段程式碼都是孤兒。

這篇講的就是我怎麼回應這四面牆。核心是一個比喻：把整個 repo 當成鑄造廠，鑄出來的不是「diff」，是有身分證的程式細胞——它有名字、有指紋、有狀態、有 evidence，可被治理、可被審計、可被未來重新組裝。

2. 原子鑄造廠：把程式碼變成有身分的細胞

「原子」（atom）這個詞在這裡有非常具體的意思。它不是 task、不是 commit、不是 prompt。它是一個有規格的程式細胞：

  • 有名字：每個 atom 有唯一 ID，例如 ATM-MAP-0042
  • 有語意指紋：input 簽章 + output 簽章 + 不變量會被正規化後做 SHA256，這就是 CID
  • 有版本與狀態：active / deprecated / expired / quarantined
  • 有 caller graph：誰呼叫它、它呼叫誰，都被記錄
  • 有 evidence 履歷：每次改動都會留 SHA256 證據
  • 會生長：可以分裂（split）、可以融合（merge）、可以演化（evolve）、可以休眠（sweep）

講白一點，一個 atom 在 registry 裡長這樣——它不是一段浮動的程式碼，而是一筆有欄位、有指紋、有履歷的紀錄：

{
  "atomId": "ATM-MAP-0042",
  "name": "idempotent-http-retry",
  "status": "active",
  "semanticFingerprint": "cid:a3f9c2e81b40",   // ← 這就是它的身分證
  "inputs":  ["url: string", "opts: RetryOpts"],
  "outputs": ["Promise<Response>"],
  "invariants": ["same idempotencyKey => at most one effect"],
  "callers": ["ATM-MAP-0017", "ATM-MAP-0031"],   // 誰在用它
  "bornBy": "behavior.atomize",
  "evidenceRefs": ["TASK-AAO-0042.closure-packet.json"]
}

所以鑄造廠的隱喻是準確的。一座工廠出貨的是組裝好的成品；一座鑄造廠出貨的是每件都帶序號的鑄件。鑄件可以單獨追溯、單獨入庫、單獨被下一個產品引用。程式碼也應該如此。

當你的 repo 進入這個模式之後，AI Agent 的工作就會變成「鑄造新原子」或「對既有原子做受治理的變換」。它沒有辦法寫一段沒有身分的浮動程式碼，因為鑄造廠不接受沒有序號的東西。

3. 治理骨架：七階生命週期 + 五個原子 + 十一個行為

講「煞車」之前要先講「煞車裝在哪」。鑄造廠的骨架不是「派一個 Agent 從頭做到尾」，而是把一次完整工作拆成七個可被機器偵測的階段，並在每階段用「原子（atom）」與「行為（behavior）」這兩個對外穩定的合約來綁住變動。下面這張圖是現況實作（不是 roadmap）：

什麼是 atom（原子）？它不是 task 也不是 commit，而是有唯一 ATM-{BUCKET}-{NNNN} 編號、有 hash-locked spec、有 evidence-required 驗證指令的最小治理單位。目前註冊表中有 5 個 active 原子（governed tier）：種子（0001）、中性掃描器（0003）、原子生成器（0004）、語意指紋（0005）、生成器自證 fixture（FIXTURE-0001）。不能直接編輯 atomic-registry.json——所有新原子必須走 ATM-CORE-0004，且須過 INV-ATM-003 的 schema gate（這就是 charter 的紅線之一）。

什麼是 behavior（行為）？對原子做的合法動詞，全部集中於 plugin-behavior-pack，按家族分類：

Split 家族

split 把既有原子拆成更清楚的範圍；atomize 從廣域 / legacy 抽出一個全新的可治理原子。

Merge 家族

merge 兩原子合一；dedup-merge 為去重而合；compose 把多個治理單位組合成更高層成品。

Evolution 家族

evolve 同一原子版本前進；polymorphize 身分不變但走變體 / 替代形式。

Lifecycle 家族

expire 正式退役；sweep 清理過時殘留。此家族目前仍在 dry-run / proposal 狀態，不直接 host apply。

Propagation 家族

infect 把治理變更外推到下游依賴，必過 neutrality scan + human review。這是「原子市場」（§10）的傳遞機制。

七階對映角色矩陣

原子在哪些階段「主導 / 協同 / 偵測 / 不介入」是有矩陣可查的。例如語意指紋（0005）分布最廣（NEXT / EXECUTE / EVIDENCE / HANDOFF / CLOSURE 都有角色）。

關於「15 角色 4 層協作」：這不是現況，是 Team Agents lane（規劃中）對未來分工的設計提案。現況實作的是「七階 + 五原子 + 十一行為 + 七條 INV-ATM」這四套合約，由 onefile runner 透過 node atm.mjs <command> 對外提供。把它們看清楚以後，後面三節（CID、lease、證據鏈）才有正確的依附對象。

4. 5D CID：給每個原子的多維身分證

這是整個鑄造廠隱喻的核心。每個 atom 都有一張身分證——CID（content-addressable identifier）。它不是「程式語意」的指紋（那是計算機科學上做不到的事），而是這個原子對外宣告的合約指紋。

誠實的邊界先講清楚：CID 是確定性的——不讀原始碼、不解析 AST、不呼叫 LLM、不算 embedding。它 hash 的是 atom 自己宣告出來的合約欄位（input/output ports、語言、是否要 evidence、效能預算）。同一份宣告永遠得到同一張證；任何非確定性訊號（向量、模型、時間戳）都不准進這把雜湊鎖。

用一個具體例子走一次。假設兩個 Agent 各寫了一個 retry helper，實作寫法不同，但他們宣告了一樣的對外合約：

// 寫法 A：for 迴圈
async function retry(url, opts) { /* ... */ }

// 寫法 B：while 迴圈、箭頭函式
const withRetry = async (u, o) => { /* ... */ };

實作不同，所以「字面雜湊」（CID.Strict）會不同。但他們的 atom spec 宣告了同樣的對外合約：

// 兩個 atom 各自的 atom spec（這才是 CID 真正去 hash 的對象）
const spec = {
  inputs: [
    { name: "url",  kind: "string" },
    { name: "opts", kind: "RetryOpts" }
  ],
  outputs: [
    { name: "result", kind: "Promise<Response>" }
  ],
  language: { primary: "typescript" },
  validation: { evidenceRequired: true },
  performanceBudget: { hotPath: false, inputMutation: "forbidden", maxDurationMs: 5000 }
};

// CID.Interface = SHA256 over the normalized declared contract
const cidInterface = "sf:sha256:" + sha256(canonicalize(spec));

// 因為兩個 atom 宣告的合約一致，所以：
//   A → sf:sha256:a3f9c2e8…1b40
//   B → sf:sha256:a3f9c2e8…1b40   ← 同一張 CID.Interface

注意這裡沒有「抽 effects」、「抽 invariants」、「砍變數名」這種事。CID 不去推測程式碼在做什麼，它只看 atom 自己明文承諾了什麼介面與執行約束。介面一致 → 雜湊一致 → 同一張身分證——這是工程上可實現的，也是目前 ATM 已經在跑的。

身分這件事其實有五個維度，目前只有 CID.Interface 已經實作，其餘四個是 roadmap 提案：

維度它認證什麼狀態
CID.Strict正規化原始碼的 SHA256，用於 git 層級竄改檢查部分（capsule / hash-lock）
CID.Interface上面那張，宣告式合約指紋✅ 已實作（=現況 semanticFingerprint）
CID.Effects副作用標籤（NET / FS / DB…），純函數 vs IO 不可替換提案，未實作
CID.Semanticembedding 向量，只當去重候選排序提示提案，未實作
CID.Behavior綁 test harness id：「在這組測試下不可區分」提案，未實作

後三個（Effects / Semantic / Behavior）永遠不會混進 identity hash——它們是 advisory，不是身分。這條防火牆叫確定性原則：身分必須穩定、可重算、不隨模型版本飄移。

有了這張證，下面這些事就變得可能（也誠實標清楚哪些已經在跑、哪些還在 roadmap）：

  • 專案內介面去重（已實作）：Dedup Police 用 CID.Interface 前綴比對，秒抓「兩個 atom 對外宣告一模一樣，要不要合併？」——這是 advisory finding，不會自己動手。
  • 跨專案介面查詢（已實作的查詢層 + 待補的索引）：在你機器上既有的 ATM repos 內，這個查詢已經可以跑；跨組織的查詢還沒有。
  • 跨組織原子市場（roadmap，需先把本地端跑成熟）：見最後一段「§10」的誠實邊界。

CID 順便解決了一個老問題：「我這個 codebase 有多少地方對外介面其實一模一樣？」這以前要靠靜態分析勉強猜，現在因為每個 atom 都帶確定性指紋，變成一個 O(1) 查表問題。但要強調——介面一致 ≠ 行為等價。後者要靠執行期測試（這就是 roadmap 上 CID.Behavior 與零信任沙盒在做的事），CID 本身只負責「誰宣稱了什麼合約」這一層。

關於 CID.Behavior 與 Tier 3 的兩條紀律（roadmap 鐵律）
  • 突變測試 / 對抗 QA 永不掛同步 close 路徑：這類測試慢、耗算力，硬塞進 atm tasks close 的同步阻擋路徑會把整條治理鏈卡死。正確做法是同步 close 時把 CID.Behavior 標為 pending 或 candidate，由 async Police / Behavior Police 在背景跑，過了才把 Tier 3 badge 掛上去。執行前必須先寫好 budget / cap / sampling / sharding / timeout 的算力保護政策，避免測試本身變成算力災難。
  • Tier 3「防竄改」必須有外部 attestation：本機 sandbox 證據只能達 Tier 2（防混亂、不防竄改）。要升到 Tier 3 / marketplace-grade，closure 必須帶外部 AttestationProvider 的簽章與可驗證 provenance——以 GitHub Actions 作為第一個 reference adapter（attestation API + OIDC），但核心維持抽象，不與單一 CI 平台硬綁定。本機 agent / 本機 Deno sandbox / 本機 daemon 都不是信任根，簽章來源才是。

5. 權限就是裝備：lease 取代資料夾隔離

兩個 Agent 不可能同時拿到同一張寫入權，因為這層在 git 之前就攔下來了。

多 Agent 並行最容易撞牆的地方是「誰可以寫什麼」。傳統做法是用資料夾權限或工具白名單，但這兩種方式都有同一個問題：它們是靜態的，不會隨著任務變化。

鑄造廠的做法是把權限拆成命名物件，每個都有 mode 屬性：

權限模式誰預設拿意義
task.lifecycleexclusiveCaptainclose / checkpoint / advance
git.writeexclusiveCaptainstage / commit / tag / push
file.writeexclusiveImplementer寫 source；範圍必須是 allowedFiles 子集
file.readshareable多人讀檔案與 source
exec.validatorshareable多人跑不會 mutate 的驗證指令
database.writeexclusive顯式授權寫外部 DB；不在預設 recipe
ci.writeexclusive顯式授權觸發或修改 CI
web.downloadexclusive顯式授權下載外部資料或套件

exclusive 權限同一時間只能有一個持有者。第二個 Agent 要拿，框架直接回 ATM_TEAM_PERMISSION_CONFLICT 錯誤碼，連 git 都還沒跑。實際跑起來長這樣：

$ node atm.mjs team lease --agent builder-01 \
    --permission file.write --paths "packages/cli/src/commands/**"
✓ lease granted — file.write → builder-01

# 另一個 Agent 想同時拿同一把寫入權：
$ node atm.mjs team lease --agent builder-02 \
    --permission file.write --paths "packages/cli/src/commands/**"
✗ ATM_TEAM_PERMISSION_CONFLICT
  file.write 是 exclusive，已被 builder-01 持有（自 12:04:11）
  → builder-02 要嘛等釋放，要嘛換一塊不衝突的 scope

權限可以轉交，但必須走 team lease 與 team release CLI，每一次轉交都留時間戳、agentId、權限範圍。這份 lease 履歷會跟著 closure-packet 一起進入永久證據。

現況 vs roadmap 的誠實邊界：上面這張權限表與 team lease CLI 是 Team Agents lane（規劃中）對未來分工的設計提案。現況已實作的最小可用集合是：ScopeLockRecord（schema atm.governanceScopeLock）的 leaseId + heartbeatAt + ttlSeconds + taskDirectionLock.allowedFiles + INV-ATM-002「lock-before-edit」doctor 守則。leaseEpoch（fencing token）/ wait-for graph 死鎖偵測 / symbol-scope lease 屬於 E2 roadmap，尚未實作。但即使只有現況的 lease + INV-ATM-002，「未鎖編輯被偵測 → 下次 atm next 回 blocked → 引導 acquire」這條煞車已經可運作。

6. 共享記憶：charter 是最高權威、ATMChart 是執行期煞車、closure-packet 是證據鏈

多 AI 協作最容易翻車的另一個點是「上下文漂移」——Agent A 跟我講過一個假設，Agent B 進場時不知道，於是寫出來的程式碼跟 A 不一致。等發現時，三個檔案都飄在四處。鑄造廠的對策不是「靠 prompt 提醒」，而是把治理規則寫成三層被機器讀的合約：

  • 最高權威 = atomic charter（.atm/charter/atomic-charter.md）+ 7 條 INV-ATM。Charter 是 framework 的最終裁判，當前版本 v2.0.0；INV-ATM-001~007 是不可逾越的紅線（由 gate / doctor / waiver-required 三種機制執行）。違反 invariant 不能繞過，必須走 charter waiver 流程（behavior.evolve + charterWaiver + HumanReviewDecision）。
  • 執行期煞車 = ATMChart（.atm/memory/atm-chart.md）的 SHA256 drift detection。它不是最高權威，但它是「拿著過期地圖會被當場攔下」的那把鎖。
  • 證據鏈 = closure-packet.v1。每次 close 寫入永久 ledger，可被半年後 audit 逐條重放。

下面把後兩個機制（ATMChart、closure-packet）攤開講；7 條 INV-ATM 留到 §7 跟警察家族一起講。

ATMChart 漂移偵測

把 5 份核心治理 schema（guards、charter、integrations、agent-prompt、upgrade-proposal）用 SHA256 鎖進 .atm/memory/atm-chart.md 的 frontmatter。任何 schema 改動 → drift → ATM_CHART_STALE 直接擋，AI 不能拿著過期地圖去動手。每張地圖都附 framework 版本與支援範圍，舊版本進場會被 ATM_CHART_VERSION_UNSUPPORTED 拒絕。

Closure-packet 證據鏈

每張卡 close 時寫入 atm.closurePacket.v1：commitDelta、commandRuns（每條指令的 stdout/stderr SHA256）、runnerVersion、teamRunId。半年後你可以重新驗證「當時跑的指令輸出，跟今天重跑是否一致」。這條 hash chain 就是 ATM 跟「PR 註解」最大的差別。

一份 closure-packet 攤開來長這樣——它記的不是「我覺得我做完了」，而是「我跑了哪些指令、各自的退出碼、輸出的 SHA256 是多少」：

{
  "schemaId": "atm.closurePacket.v1",
  "taskId": "TASK-AAO-0042",
  "commandRuns": [
    { "command": "npm run typecheck",
      "exitCode": 0,
      "stdoutSha256": "sha256:dade4751…655da0" },
    { "command": "node atm.mjs test --spec",
      "exitCode": 0,
      "stdoutSha256": "sha256:9f1c0a…b3e7" }
  ],
  "commitDelta": { "changedFiles": 3, "governedTreeSha": "9f1c2d…" },
  "teamRunId": "team-abc123",
  "runnerVersion": "0.1.0"
}

注意 exitCode 跟 stdoutSha256 是綁在一起的。Agent 沒辦法把一個 exitCode: 1 的 validator 說成「通過」——退出碼非 0 就只能記成 diagnostic，不能算 pass。證據不會說謊。

這兩個機制合起來提供一個保證：沒有 Agent 可以宣稱「我以為規則是這樣」。規則的版本、規則的 hash、規則的支援範圍，都在地圖上明文寫著。地圖過期就會被擋，不可能裝沒看到。

7. 7 條 INV-ATM 紅線 + 9 個常駐警察：合約煞車與結構良心

你睡覺的時候，警察還在巡；invariants 一直釘在那裡，從來沒下班。

鑄造廠的「煞車」其實分兩層。合約層的煞車是 charter 上的 7 條 INV-ATM（公開、穩定、寫進 framework），偵測層的煞車是 9 個常駐警察家族（advisory、機器自動跑、報給人類定奪）。它們的分工是：

合約紅線（INV-ATM-00X）對應煞車類型白話意義
INV-ATM-001 No second registrygate（直接拒絕）整個 repo 只能有一個 atomic-registry 真相來源。
INV-ATM-002 Lock before editdoctor（引導修復）編輯前必須持有 ScopeLock。
INV-ATM-003 Schema-validated promotion onlygate所有原子升級必須過 schema 驗證，直接改 registry 禁止。
INV-ATM-004 No competing highest authoritydoctor沒有任何 host rule 可以聲稱地位等於或高於 charter。
INV-ATM-005 Host rule amendments require waiver flowwaiver-required違反 invariant 的合法路徑：behavior.evolve + charterWaiver + HumanReviewDecision。
INV-ATM-006 Framework work tracking stays target-localdoctorframework 任務 ledger 必須留在 framework repo 自己的 .atm/history/tasks/。
INV-ATM-007 Public framework docs remain English-onlydoctorframework 公開文件英文化、中性化；ATM-CORE-0003 中性掃描器負責執行。

7 條 INV-ATM 是公開合約，違反需走 charter waiver；9 個警察家族則是 advisory 偵測——它們不在 charter 上，但天天在 registry 與 source 裡巡邏，把慢性結構衰敗抓出來。一次 mutation 安全是 INV-ATM 的事；幾百次 mutation 累積後 repo 還健不健康，是警察家族的事。

9 個警察家族：

Dedup Police

掃 CID 前綴重疊。一旦 registry 裡出現兩個 atom 指紋很近，自動產 advisory finding，路由到 behavior.dedup-merge。

Demand Police

掃 caller-graph 過載。某個 atom 的呼叫者數量超過門檻（預設 6）→ 建議走 behavior.split。

Decomposition Police

用 source-inventory 算 LOC，超過神檔門檻 → 推 atomize plan draft。每日有上限避免一次刷出 100 條 finding 淹沒人類。

Quality Police

比對品質指標前後變化。回歸大於門檻 → blocker。新原子品質低於 baseline → 不過 quality gate。

Evolution / Polymorph

看 atom 是否該升級到下一版、是否該抽成 template + variants。advisory only，最終決策回人類。

Rollback Police

守 reversibility。任何 mutation 要 apply 前都要有 rollback proof。沒有就擋。這條線守住所有 map replacement / evolution / atomization / infect / expire / retirement 流程的安全。

這些警察有一個共同的鐵律：directApplyAllowed: false。它們可以發現問題、可以建議路徑、可以產出 plan draft，但它們永遠不會直接 mutate。一筆 finding 攤開來其實很樸素，重點是最後那一行：

{
  "policeFamily": "dedup",
  "severity": "advisory",
  "trigger": "semantic-fingerprint-overlap",
  "scope": "ATM-MAP-0042,ATM-MAP-0088",
  "message": "兩個 atom 的語意指紋高度重疊，建議評估合併",
  "routeHint": "behavior.dedup-merge",
  "directApplyAllowed": false   // ← 警察只通報，動手要人類批准
}

所有 apply 都要過 ReviewAdvisory machine-finding + HumanReviewDecision，人類在 advisory 升 blocker 的 promotion 是不可繞過的閘門。

這是鑄造廠刻意拒絕「24 小時全自動演進」的設計選擇——當你有 N 個 Agent 同時改 repo 時，再放一個自主重構機器人進來，是在製造寫-寫衝突風暴。警察的價值是「看見」，不是「動手」。

8. 從 git clone 到第一張卡 close：採用 ATM 的最小路徑

所有這些聽起來很複雜的東西，採用門檻其實不高。ATM 的官方分發單位是單檔 runner atm.mjs（約 3.1 MB 的 strip-types bundle，無 transitive dep）；部署是「framework 端 push 給 adopter」的顯式 sync，不是 npm install。下面是從 0 到第一張 closure-packet 的最小路徑：

# 0-15 min：取得 runner + ORIENT
# Framework 端（onefile 已 build 好）：
#   npm run build  →  release/atm-onefile/atm.mjs（約 3.1 MB）
# Adopter 端：把 onefile sync 進來
node release/atm-onefile/atm.mjs internal-release sync \
    --repo /path/to/my-app --json
cd /path/to/my-app
node atm.mjs orient --cwd . --json
node atm.mjs doctor  --cwd . --json
# 看每條 doctor 守則（lock-before-edit、charter-integrity、neutrality-scanner-active…）全綠

# 15-30 min：問 NEXT、鎖 LOCK
node atm.mjs next --prompt "your first small change" --json
# 拿到 nextAction → 依 command 字串執行（例如 lock acquire）
node atm.mjs lock acquire --workItem <workItemId> \
    --files src/foo.ts --reason "first small change" --json

# 30-60 min：EXECUTE → EVIDENCE
# 在 lock 範圍內改檔、跑你的測試
npm test
node atm.mjs evidence add --task <workItemId> --actor codex-main \
    --kind test --summary "unit tests passed" --artifacts reports/test.json --json

# 60-80 min：HANDOFF + 證據 verify
node atm.mjs evidence verify --task <workItemId> --gate close --json
node atm.mjs handoff summarize --task <workItemId> --json

# 80-90 min：CLOSURE
node atm.mjs tasks close --task <workItemId> --actor codex-main --status done --json
# 寫入 .atm/history/evidence/<taskId>/closure-packet.json
# 內含 commandRuns[].stdoutSha256 + targetCommit + governedTreeSha
# 後續任何 audit 重跑同樣命令 → byte-for-byte 比對
邊界提醒：（1）npx create-atm / examples/team-agents-minimal/ 是 Team Agents lane 規劃中的便利層，現況部署走的是上面的 internal-release sync。（2）若你的 repo 是 framework 本身，doctor 會偵測到 framework 簽名並啟用額外規則（INV-ATM-006 framework 任務必須 target-local、closure-packet 必須帶 framework gate provenance）；adopter mode 則只受通用 invariants 約束。

90 分鐘結束你會擁有什麼？

  • 一個 commit，帶 teamRunId 與 closure 證據引用
  • 一份 .atm/history/evidence/TASK-XXXX.closure-packet.json，含每一條指令的 stdout SHA256
  • 一份 patrol-report.md，記錄這張卡 close 時的結構健康度
  • 一份 team-memory-shard.md，把這次學到的教訓存進可索引的知識庫

這四樣東西是鑄造廠跟一般 vibe coding 流程最直接的差異：你不只拿到改完的程式，你還拿到永久證據、結構快照、可累積的教訓。下次開新卡，這些東西會被自動載入下一個 Agent 的上下文。

9. 容易失敗的地方（與對應的 doctor 守則）

誠實講，鑄造廠不是一鍵綠的。下面六個是我最常踩到、也是 ATM doctor 守則直接點名的場景。每一個都對應一條具體的 doctor 檢查，失敗時會回傳 firstFailedCheck 加 suggestion，agent 不需要猜：

lock-before-edit（INV-ATM-002）

未持鎖就編輯。下一次 atm next 回 blocked，suggestion 直接給 atm lock acquire --files <list>。最常見也最容易修。

evidence-freshness

任務 reopen 後想用舊證據 close。閘門擋下，要求收集 reopenedAt 之後的新證據。這條是 commit 85b92ce 加入的硬化，杜絕「悄悄重開再用舊證據 close」的繞道。

git-head-evidence

closure packet 的 targetCommit 對不上當前 git HEAD。Doctor 拒絕，要求 rebase 或重新 close。讓「封包描述的狀態 vs 實際 repo 狀態」不能漂移。

registry-sole-source（INV-ATM-001）

repo 裡跑出第二個 atomic-registry.json（通常是某 plugin「為了方便」自建）。直接 gate 拒絕，要求合併回根註冊表並走 ATM-CORE-0004。

neutrality-scanner-active（INV-ATM-007）

Framework 公開文件出現 adopter 私有名詞或非英文段落。ATM-CORE-0003 中性掃描器報 violation；改不掉就走 charter waiver。

charter-integrity

charter.md 與 charter-invariants.json 不同步（charterVersion / lastAmendedAt 對不上）。Doctor 要求對齊兩端。這是「最高權威」自身的健康檢查。

這六個坑都有一個共同特徵：它們不是 framework bug，是治理紀律問題。框架提供攔截機制 + 結構化失敗回報 + 可直接執行的修復指令，但你要把 atm doctor 接進你的 pre-commit hook / CI 步驟，這套煞車才會真正在你睡著時也運作。

10. CID-Native 原子代碼市場：北極星，不是明天就上線

到目前為止講的都是單一專案內怎麼治理。從這裡開始是 roadmap——我想先講清楚這條路真的能走的部分、跟還在 north star 階段的部分，避免賣空頭支票。

骨牌可以這樣排：CID.Interface 是確定性的，意思是同一份對外宣告 → 同一張 CID.Interface → 不分作者、不分專案。如果一萬個專案都採用同一套治理協議，每個專案都會產出帶 CID 的 atom 清單。某天你在新專案需要 idempotent-http-retry-with-jitter：

  1. 本地算這個需求的 CID.Interface 前綴
  2. 查跨組織 CID 索引
  3. 命中 N 個候選 atom（不同實作、不同語言、不同 quality / trust tier）
  4. 每個候選 atom 都帶它自己的 closure-packet、evidence、police clean record、宣告的能力（網路 / 檔案 / DB 權限）
  5. 人類審 → 通過 → atm infect 把它接進你的專案，並依本地契約建立 caller graph

它要填的位置是 npm + Docker Hub + Stack Overflow 之後一個還沒有人補上的中間層：npm 給你 package 但不告訴你內部結構，Stack Overflow 給你 snippet 但沒有任何 audit，Docker 給你 image 但顆粒太大。函式級、帶完整治理履歷、可被機器搜尋的程式細胞——這個空缺確實值得填。

但下面這些邊界要先講清楚，免得被當成「明天就能用」：
  • 市場是最後一個 epoch，不是明年：跨組織市場要先等本地端跑成熟、Trust Tier 制度化、零信任沙盒落地。目前的 ATM roadmap 把它 gated 在最後階段，且必須先在單一專案內實證 Tier 3（沙盒+對抗 QA+突變測試）。沒走完前置，跨組織市場只是空中樓閣。
  • 它不取代 npm / Docker：它跟它們不在同一層。npm 還是會繼續發 package、Docker 還是會繼續發 image。CID 原子市場處理的是「函式級 + 被治理 + 可重組」這個顆粒度，是補位，不是取代。
  • in-place resolution 不消滅依賴管理，只把它上移到介面層：infect 一個 atom 進來時，框架優先綁定你本地已經有的、滿足同樣契約的原子；本地沒有命中時，才需要從市場拉實作（這時你還是會碰到傳遞性依賴）。比 node_modules 乾淨，但不是「沒有依賴」。
  • infect 永遠是 advisory + 人審：不會「自動」把一段陌生原子接進你的程式。它跟所有 atom behaviors 一樣，受 directApplyAllowed:false 鐵律約束。

所以我會誠實地說：CID 原子市場是北極星，不是承諾的下一個版本。我目前在做的、能在合理時間內交付的，是把單一專案內的 CID.Interface + 證據鏈 + 巡邏警察跑紮實。市場是把同一套協議外推到跨組織時自然會浮現的東西——它要等地基。

說回那個我最終想看到的圖像：AI 寫的每一段程式碼，都應該是有名字、可被審計、可被找到的細胞，而不是只活在我這個 repo 的孤兒。這件事不需要等市場才能開始——從你今天打開的這個 repo，給每個 atom 一個確定性的 CID.Interface 開始，就是。

11. 結語

2025 年大家在比「我的 AI Agent 有多聰明」。2026 年我覺得該換個題目：當 N 個聰明的 Agent 同時改一個 repo 時，這個 repo 還能不能保持可治理。

我給自己的答案是鑄造廠 + 五維身分證 + 七階煞車。把每段程式碼變成有名字的細胞、把每次改動變成有 hash 的證據、把 7 條 INV-ATM 寫成 charter 紅線、讓 9 個常駐警察看著結構健康度、把 ORIENT→CLOSURE 釘成不能跳階的生命週期。這套東西聽起來規矩很多，但它的回報是：半年後我的 repo 還能讀懂、還能被審計、還能被重用——而且我同時開 5 個 Agent 也不會把它撞爛。

如果你只想做一個小 feature，這套協議是 overkill。但如果你要做一個跑半年、多個 AI 並行介入、未來可能要送合規、甚至想把寫過的好 atom 分享給世界的專案——你需要的就是這樣一座有煞車的鑄造廠。

這篇是入門介紹。如果你想看具體實作、API、police family 機制、權限模型細節，可以看 github.com/eaglhuang/AI-Atomic-Framework。框架本身是 MIT，整套治理協議可以直接 fork、可以替換成自己的 governance bundle、也可以只用其中一部分（例如只接證據鏈、只接 ATMChart）。
