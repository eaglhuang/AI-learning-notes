Why "Same File = Conflict" Is Wrong for Multi-Agent Coding: A CID-Based Parallel Conflict Advisor

When two AI coding agents both want to touch the same repo, every conflict-detection tool you have was designed for humans. It looks at filenames. That's fine for two people; it's catastrophically wrong for five agents running in parallel. Here's the layer that actually answers the question — "can these two tasks be done at the same time?" — using CID, a deterministic contract fingerprint.

by Eagl Huang · June 6, 2026 · 6 min read

The wrong question Git answers

Git's conflict detector lives at the line level: did you and I edit the same line? That's fine for two humans. With N agents, it fails in two specific ways:

  • False positives. Two agents edit different functions inside tasks.ts. Logically independent. Yet the orchestrator sees "same file" and serializes them.
  • False negatives. Two agents touch different files but both modify the same public contract of a generator or validator. Git sees no conflict. Deployment breaks.

Git solves the physical conflict: you and I edited the same line. CID solves the logical conflict: you and I touched the same contract fingerprint. Neither can substitute for the other.

What a CID actually is

A CID (content-addressable identifier) is a deterministic SHA256 over the contract an atom declares for itself — its input/output ports, its language, its performance budget, its evidence requirement. The key word is deterministic: no source parsing, no AST analysis, no LLM call, no embedding. Same declaration → same fingerprint, every time.

That deterministic property is what makes CID usable as a conflict signal. If your two tasks both modify the atom cid:sha256:a3f9c2e8…1b40, you have a real semantic collision, regardless of which files you touched. If they touch cid:sha256:a3f9 and cid:sha256:b7d1 respectively, you can run them in parallel even when the files overlap.

Eight verdicts the advisor emits

Given two tasks A and B, the parallel conflict advisor returns one of these:

VerdictAction
parallel-safeDifferent CIDs, no file overlap, no shared surface → agents work independently.
needs-physical-splitDifferent CIDs but overlapping file ranges → run in parallel, merge via deterministic composer.
blocked-cid-conflictSame atom_cid → real semantic conflict; serialize or split the atom.
blocked-shared-generatorSame code generator → serialize.
blocked-shared-validatorSame validator → serialize.
blocked-shared-projectionSame view/index → serialize.
blocked-shared-artifactSame output artifact → serialize.
blocked-active-leaseAnother active lease already holds the scope → wait.

The middle case, needs-physical-split, is what file-based tools can't even express. Two agents legitimately work on different logical concerns that happen to live in the same file — the right answer is "go ahead, here's the merge plan," not "one of you wait."

It doesn't just block — it tells you how to split

When a real conflict shows up, the advisor returns a merge plan with:

  • Reason: the specific CID / generator / artifact that collided.
  • Recommended lane: deterministic composer, Neutral Write Steward, or shared-surface guard.
  • Hotspot report: how many times this point has collided across recent tasks — the higher the count, the more urgent it is to refactor that atom.
  • Required evidence: which validators must pass before the merged change can close.
Key insight: this is a logical-layer solution, not a physical one. Git handles the physical layer (history, branches, merges, rollbacks). CID handles the contract layer. Without atoms and atom maps, CID has nothing to point at; without CID, multi-agent parallelism falls back to "same file = locked" — a heuristic from the human-pair era that doesn't survive five agents in one repo.
