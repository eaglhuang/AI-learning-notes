The Atomic Foundry: Giving Every Piece of Code an Identity, Evidence, and a Second Life When N AI Agents Build One Project

Picture your whole repo as a foundry. Every time an AI agent finishes a piece of code, the foundry hands it an ID card, a SHA256 evidence packet, and a fingerprint that anyone can look up later. What gets cast is not an anonymous diff — it is a code cell with a name, a file, and the ability to be searched and reused by other projects across the world. This piece walks through why I ended up here, which multi-agent pain points it solves, and how a single engineer can start using it today.

1. The walls you hit when many AIs build one project at once

Around day thirty you realize that babysitting three agents on your repo is more tiring than just writing it yourself.

Coding with a single AI assistant feels great at first. It fills in files, writes tests, drafts your README — progress without typing. Then you open a few more: one agent on this task, another on that one, a third opening a PR in your editor. You expect 3× the speed; you hit three walls.

The first wall is reinvented work. Agent A writes an HTTP retry helper. Three weeks later Agent B writes an almost identical one in another feature. Two weeks after that, Agent C writes a third. Nobody notices "this already exists semantically," because each agent only sees its own slice.

The second wall is scope collisions. Three agents edit one repo with no mechanism telling them "someone is already touching this file" or "this write permission can go to only one of you this round." You find out at git merge — far too late.

The third wall is slow structural decay. Every feature is correct, yet six months later files keep swelling, tasks.ts grows from 300 lines to 1,500, and nobody is watching for "this file should be split" or "twelve of these thirty atoms are semantic duplicates." Each part is fine; the whole is quietly rotting. This is structural entropy, and it never shows up in any single PR — it's a chronic condition that only time reveals.

The fourth wall is the subtlest — no identity. However beautifully it's written, every snippet an AI produces is an anonymous string that lives only in that project's git history. If a helper in the project next door is semantically identical, the two never know about each other, and the next new project can't recognize either. Every piece of code is an orphan.

This article is how I answer those four walls. The core is one metaphor: treat the whole repo as a foundry. What it casts is not a "diff" but a code cell with an ID card — it has a name, a fingerprint, a status, and evidence. It can be governed, audited, and reassembled later.

2. The atomic foundry: turning code into cells with identity

The word "atom" means something very specific here. It is not a task, not a commit, not a prompt. It is a code cell with a spec:

  • It has a name: every atom has a unique ID, e.g. ATM-MAP-0042
  • It has a semantic fingerprint: input signature + output signature + invariants are normalized and SHA256-hashed — that is the CID
  • It has a version and a status: active / deprecated / expired / quarantined
  • It has a caller graph: who calls it and what it calls are both recorded
  • It has an evidence history: every change leaves a SHA256 record
  • It grows: it can split, merge, evolve, or go dormant (sweep)

In plain terms, here's what an atom looks like in the registry — not a floating snippet, but a record with fields, a fingerprint, and a history:

{
  "atomId": "ATM-MAP-0042",
  "name": "idempotent-http-retry",
  "status": "active",
  "semanticFingerprint": "cid:a3f9c2e81b40",   // ← this is its ID card
  "inputs":  ["url: string", "opts: RetryOpts"],
  "outputs": ["Promise<Response>"],
  "invariants": ["same idempotencyKey => at most one effect"],
  "callers": ["ATM-MAP-0017", "ATM-MAP-0031"],   // who uses it
  "bornBy": "behavior.atomize",
  "evidenceRefs": ["TASK-AAO-0042.closure-packet.json"]
}

So the foundry metaphor is precise. A factory ships finished assemblies; a foundry ships castings, each stamped with a serial number — traceable on its own, with its own recipe, ready to flow into the next product. Code should work the same way.

Once your repo enters this mode, an AI agent's job becomes "cast a new atom" or "apply a governed transformation to an existing one." It cannot write a floating, identity-less snippet, because the foundry refuses anything without a serial number.

3. Fifteen roles across four layers

A layered team runs the foundry: decisions on top, trades in the middle, evidence at the bottom, patrol police standing watch on the side. That is a very different shape from "send one worker end to end." Meet them in a team photo first:

Now put the cast back into their actual collaboration layers:

L1 Decision: the Captain is the sole lifecycle owner

However many agents you run, only the Captain can close tasks, checkpoint, commit, or push. That rule is baked into the framework — with five agents running at once, no single decision point means chaos. For complex tasks, a Lieutenant helps split phases.

L2 Trades: each role holds a "permission," not a "tool"

The Atomization Planner does atomization planning first; the Scope Sentinel guards the allowedFiles boundary; the Code Builder is the only holder of file.write at that moment; QA / Check Runner runs validation. Their isolation does not come from folders or from politely asking the AI "please don't touch that" — it comes from a permission model, covered next.

L3 Evidence: every change leaves an auditable trace

The Evidence Curator collects the commands the Builder ran, the SHA256 of stdout/stderr, and validator results into an atm.closurePacket.v1. The Closure Steward audits that packet before close. This evidence is not a PR comment — it is a permanent file in .atm/history/, schema-versioned, ready for an external compliance audit.

L4 Patrol: the repo's own structural conscience

Nine atomic police families plus six patrol moments (daily, pre-claim, pre-close, pre-checkpoint, pre-big-script, multi-agent collision) belong to the repo, not to any one task. Their job is to see structural decay — overlapping fingerprints, oversized files, overloaded caller graphs, expired TTLs — and emit a readable patrol report.

4. CID: an ID card for every atom

This is the heart of the foundry metaphor. Every atom carries an ID card — a CID (content-addressable identifier). It is not a fingerprint of "what the code means" (that's something computer science can't actually deliver). It's a fingerprint of what the atom publicly declares it does.

The honest boundary, up front: a CID is deterministic — no source parsing, no AST analysis, no LLM call, no embedding. What it hashes is the contract fields the atom declares for itself (input / output ports, language, evidence requirement, performance budget). The same declaration always yields the same card; any non-deterministic signal (vectors, model outputs, timestamps) is forbidden from this hash.

A concrete example. Two agents write a retry helper. The implementations look completely different:

// Version A: for-loop
async function retry(url, opts) { /* ... */ }

// Version B: while-loop, arrow fn
const withRetry = async (u, o) => { /* ... */ };

Different implementations, so their literal-source hash (CID.Strict) differs. But both atoms declared the same outward contract:

// Each atom's own atom spec — this is what CID actually hashes
const spec = {
  inputs: [
    { name: "url",  kind: "string" },
    { name: "opts", kind: "RetryOpts" }
  ],
  outputs: [
    { name: "result", kind: "Promise<Response>" }
  ],
  language: { primary: "typescript" },
  validation: { evidenceRequired: true },
  performanceBudget: { hotPath: false, inputMutation: "forbidden", maxDurationMs: 5000 }
};

// CID.Interface = SHA256 over the normalized declared contract
const cidInterface = "sf:sha256:" + sha256(canonicalize(spec));

// Because both atoms declared the same contract:
//   A → sf:sha256:a3f9c2e8…1b40
//   B → sf:sha256:a3f9c2e8…1b40   ← same CID.Interface

Notice what's not happening: no "effects extraction," no "invariants inferred," no "variable names stripped." The CID doesn't guess what the code does — it reads what the atom publicly promised as its interface and execution constraints. Matching declarations → matching hashes → same ID card. This is engineering-tractable, and it's what ATM already runs today.

Identity actually has five possible dimensions; only CID.Interface is shipped right now. The rest are roadmap:

DimensionWhat it certifiesStatus
CID.StrictSHA256 of normalized source; for git-level tamper checkspartial (capsule / hash-lock)
CID.InterfaceThe one above — declared contract fingerprint✅ shipped (= today's semanticFingerprint)
CID.EffectsEffect tags (NET / FS / DB…); pure vs IO can't substituteproposed, not built
CID.SemanticEmbedding vector; only as a ranking hint for dedup candidatesproposed, not built
CID.BehaviorBound to a test-harness id: "indistinguishable under this harness"proposed, not built

The last three (Effects / Semantic / Behavior) will never be mixed into the identity hash — they're advisory, not identity. This firewall is the determinism axiom: identity has to be stable, recomputable, and unaffected by model-version drift.

With that card in hand, here's what becomes possible — flagged honestly with what already runs and what's still on the roadmap:

  • In-project interface dedup (shipped): the Dedup Police compares CID.Interface prefixes and instantly catches "two atoms declared the exact same contract — should they merge?" This is an advisory finding; it never auto-acts.
  • Cross-project interface lookup (query layer shipped; cross-org index pending): across ATM repos already on your machine, this lookup works today; a true cross-organization index does not yet exist.
  • Cross-organization atom market (roadmap, gated by local maturity): see §10 for the honest boundary.

CIDs also resolve an old question: "how much interface-level duplication does my codebase have?" That used to be fragile static analysis; now that every atom carries a deterministic fingerprint, it's an O(1) lookup. One caveat to be loud about — matching interface ≠ matching behavior. The latter belongs to runtime testing (which is where CID.Behavior and the zero-trust sandbox are headed on the roadmap). CID itself only covers the layer of "who declared what contract."

5. Permission is the gear: leases replace folder isolation

Two agents cannot hold the same write key at the same time — this layer stops it before git ever runs.

The place multi-agent work crashes hardest is "who may write what." The traditional answer is folder permissions or tool allowlists, and both share a flaw: they are static and don't change with the task.

The foundry splits permission into named objects, each with a mode:

PermissionModeDefault holderMeaning
task.lifecycleexclusiveCaptainclose / checkpoint / advance
git.writeexclusiveCaptainstage / commit / tag / push
file.writeexclusiveImplementerwrites source; scope must be a subset of allowedFiles
file.readshareablemanyread files and source
exec.validatorshareablemanyrun non-mutating validation commands
database.writeexclusiveexplicit grantwrite external DB; not in the default recipe
ci.writeexclusiveexplicit granttrigger or modify CI
web.downloadexclusiveexplicit grantdownload external data or packages

An exclusive permission has only one holder at a time. When a second agent reaches for it, the framework returns ATM_TEAM_PERMISSION_CONFLICT before git is even involved. Live, it looks like this:

$ node atm.mjs team lease --agent builder-01 \
    --permission file.write --paths "packages/cli/src/commands/**"
✓ lease granted — file.write → builder-01

# A second agent reaches for the same write key:
$ node atm.mjs team lease --agent builder-02 \
    --permission file.write --paths "packages/cli/src/commands/**"
✗ ATM_TEAM_PERMISSION_CONFLICT
  file.write is exclusive and already held by builder-01 (since 12:04:11)
  → builder-02 must wait for release, or take a non-overlapping scope

Permissions can be handed over, but only through team lease and team release on the CLI — every handover records a timestamp, the agent ID, and the permission scope. That lease history travels with the closure-packet into permanent evidence.

6. ATMChart and the evidence chain: shared memory that isn't word of mouth

The other place multi-AI work tips over is context drift — Agent A told me an assumption, Agent B never heard it, and so B writes code inconsistent with A. By the time you notice, three files are adrift.

The foundry pins shared memory down with two mechanisms:

ATMChart drift detection

Five core governance schemas (guards, charter, integrations, agent-prompt, upgrade-proposal) are SHA256-locked into the frontmatter of .atm/memory/atm-chart.md. Any schema change → drift → ATM_CHART_STALE blocks it: an AI cannot act on a stale map. Every chart carries the framework version and supported range; an old version is rejected with ATM_CHART_VERSION_UNSUPPORTED.

Closure-packet evidence chain

Each task writes an atm.closurePacket.v1 on close: commitDelta, commandRuns (the SHA256 of each command's stdout/stderr), runnerVersion, teamRunId. Months later you can re-verify whether the recorded output still matches a fresh run. That hash chain is the biggest difference between ATM and a "PR comment."

Opened up, a closure-packet looks like this — it records not "I think I'm done," but "which commands I ran, their exit codes, and the SHA256 of their output":

{
  "schemaId": "atm.closurePacket.v1",
  "taskId": "TASK-AAO-0042",
  "commandRuns": [
    { "command": "npm run typecheck",
      "exitCode": 0,
      "stdoutSha256": "sha256:dade4751…655da0" },
    { "command": "node atm.mjs test --spec",
      "exitCode": 0,
      "stdoutSha256": "sha256:9f1c0a…b3e7" }
  ],
  "commitDelta": { "changedFiles": 3, "governedTreeSha": "9f1c2d…" },
  "teamRunId": "team-abc123",
  "runnerVersion": "0.1.0"
}

Note how exitCode and stdoutSha256 are bound together. An agent cannot pass off an exitCode: 1 validator as "passing" — a non-zero exit can only be recorded as a diagnostic, never as a pass. Evidence cannot lie.

Together these two mechanisms guarantee one thing: no agent can claim "I thought the rule was X." The rule's version, hash, and supported range are written on the map in plain sight. A stale map gets blocked — there's no pretending you didn't see it.

7. Nine resident police: the repo's own structural conscience

While you sleep, the patrol keeps walking.

Everything so far has been about "making one mutation safe." But structural decay never appears in a single mutation — it accumulates over time. So the foundry keeps a resident police family:

Dedup Police

Scans for CID prefix overlap. The moment two atoms have near-identical fingerprints, it emits an advisory finding routed to behavior.dedup-merge.

Demand Police

Scans for caller-graph overload. When an atom's caller count crosses a threshold (default 6) → it recommends behavior.split.

Decomposition Police

Uses source-inventory to count LOC; over the god-file threshold → it drafts an atomize plan. A daily cap stops it from flooding a human with 100 findings at once.

Quality Police

Compares quality metrics before and after. Regression over threshold → blocker. A new atom below baseline → it fails the quality gate.

Evolution / Polymorph

Watches whether an atom should upgrade to a next version, or be abstracted into a template + variants. Advisory only; the final call returns to the human.

Rollback Police

Guards reversibility. Any mutation must have rollback proof before apply, or it's blocked. This line protects every map replacement / evolution / atomization / infect / expire / retirement flow.

These police share one iron rule: directApplyAllowed: false. They can find problems, suggest routes, and draft plans, but they never mutate directly. A finding, opened up, is quite plain — the line that matters is the last one:

{
  "policeFamily": "dedup",
  "severity": "advisory",
  "trigger": "semantic-fingerprint-overlap",
  "scope": "ATM-MAP-0042,ATM-MAP-0088",
  "message": "Two atoms have highly overlapping fingerprints; consider merging",
  "routeHint": "behavior.dedup-merge",
  "directApplyAllowed": false   // ← police only report; acting needs a human
}

Every apply must pass ReviewAdvisory machine-finding + HumanReviewDecision; the human promotion from advisory to blocker is a gate you cannot route around.

This is the foundry deliberately refusing "24/7 fully automatic evolution." When N agents are editing the repo at once, dropping in an autonomous refactoring robot is just manufacturing write-write conflict storms. The value of the police is to see, not to touch.

8. Ninety minutes: from git clone to a first closed task

For all of this complexity, the adoption barrier is low. The promise I set myself: from a clean environment to a first AI-completed task formally closed, in under ninety minutes. Minute by minute:

# 0-15 min: environment up
npx create-atm my-app --agent claude-code
cd my-app
node atm.mjs doctor --json
# watch 15+ health checks go green

# 15-30 min: copy the minimal example + edit 4 fields
cp -r node_modules/ai-atomic-framework/examples/team-agents-minimal/. .atm/team/
# edit team-brief.md: task title, goal, allowedFiles, expectedReport

# 30-60 min: the agent edits code
node atm.mjs next --prompt "your first small change" --json
# agent gets routing → claim → touch only allowedFiles → run typecheck

# 60-80 min: verify and collect evidence
node --strip-types scripts/validate-team-agents-templates.ts
# write agent-report.md and team-summary.md

# 80-90 min: close
node atm.mjs tasks close --json
# auto-emits closure-packet.json (with SHA256) + the first patrol-report.md

What do you own at the ninety-minute mark?

  • A commit carrying a teamRunId and a reference to its closure evidence
  • A .atm/history/evidence/TASK-XXXX.closure-packet.json with the stdout SHA256 of every command
  • A patrol-report.md recording the structural health at close time
  • A team-memory-shard.md filing this task's lesson into a searchable knowledge base

Those four are the most direct difference between the foundry and ordinary vibe coding: you don't just get finished code — you get permanent evidence, a structural snapshot, and an accumulating lesson. Next time you open a task, these are loaded into the next agent's context automatically.

9. Where it tends to fail

Honestly, the foundry is not green on the first try. These are the potholes I hit most:

Scope leak

An agent holds file.write but touches files outside its lease paths. The framework raises ATM_TEAM_WRITE_SCOPE_EXCEEDED, but you have to set up the forbidden_files allowlist for it to bite. Plain text in a task card won't stop it — you need dual-agent dispatch plus physical path isolation.

Evidence faking

An agent reports a failing validator as a pass. This is the most fatal wound to an evidence system. The countermeasure: the Evidence Curator must record exitCode and stdout SHA256; a non-zero exit can only be a diagnostic, never a pass.

Unreleased lease

An agent takes git.write, crashes without releasing, and the next task is stuck. The countermeasure: leases carry TTL + heartbeat, and a scheduler can reclaim stale locks.

Stale ATMChart nobody re-renders

A rule changes a schema but nobody re-renders → the next agent is blocked on entry. The countermeasure: wire atm-chart render into a pre-commit hook so the map always tracks the rules.

All four share a trait: they are not framework bugs, they are governance-discipline problems. The framework provides the interception; you have to wire it into your hooks, CI, and dispatch flow for it to actually hold.

10. A CID-native atom market: the north star, not next month's release

Everything so far has been about a single project. From here on, this is roadmap territory — and I want to draw the line clearly between what this road can actually deliver and what's still north star, so I don't sell empty promises.

The dominoes line up like this: CID.Interface is deterministic, which means the same outward declaration produces the same CID.Interface regardless of author or project. If ten thousand projects adopt the same governance protocol, each produces a list of CID-bearing atoms. One day in a new project you need idempotent-http-retry-with-jitter:

  1. Locally compute the requirement's CID.Interface prefix
  2. Query the cross-organization CID index
  3. Match N candidate atoms (different implementations, languages, quality / trust tiers)
  4. Each carries its own closure-packet, evidence, clean police record, and declared capabilities (network / file / DB permissions)
  5. A human reviews → approves → atm infect wires it into your project, building the caller graph against your local contracts

What it would fill is a real gap that sits after npm + Docker Hub + Stack Overflow and isn't covered by any of them: npm gives you a package but not its internal structure, Stack Overflow gives you a snippet with no audit, Docker gives you an image at far too coarse a grain. Function-grain, governance-laden, machine-searchable code cells — yes, this slot deserves to exist.

But these boundaries need to be stated up front, before anyone treats this as "shippable next month":
  • The market is the last epoch, not next year: a cross-organization market depends on the local layer being mature first — Trust Tier institutionalized, the zero-trust sandbox shipped. The current ATM roadmap gates it as the final stage and conditions it on Tier 3 (sandbox + adversarial QA + mutation testing) being proven inside a single project. Until those prerequisites land, the market is castles in the air.
  • It does not replace npm or Docker: it sits at a different layer. npm will keep shipping packages and Docker will keep shipping images. The CID market handles the "function-grain, governed, recomposable" granularity — it fills a gap, it doesn't supplant.
  • In-place resolution doesn't abolish dependency management; it lifts it up to the contract layer: when you infect an atom, the framework first binds it to whatever local atoms already satisfy the same contract. Only when nothing local matches does it actually pull an implementation from the market (and at that point you still face transitive dependencies). Cleaner than node_modules, but not "dependency-free."
  • Infect is always advisory + human-reviewed: nothing wires a stranger's atom into your code automatically. Like every other atom behavior, it's bound by the directApplyAllowed:false iron rule.

So, honestly: the CID atom market is the north star, not a promised next version. What I'm actually building and can deliver on a sensible timeline is to make CID.Interface + the evidence chain + the patrol police work solidly inside a single project. The market is what naturally emerges when the same protocol gets stretched across organizations — it needs ground beneath it first.

Back to the picture I ultimately want to see: every piece of code an AI writes should be a named, auditable, findable cell — not an orphan living only in my repo. That doesn't have to wait for the market. It can start with the repo you're already in today, the moment every atom gets a deterministic CID.Interface.

11. Closing

In 2025 everyone competed on "how smart is my AI agent." In 2026 I think the question should change: when N smart agents edit one repo at once, can that repo stay governable?

My answer is the foundry. Turn every piece of code into a named cell, every change into a hashed evidence record, let nine resident police watch structural health, and split fifteen roles by responsibility. It sounds like a lot of rules, but the payoff is this: six months later, my repo is still readable, still auditable, still reusable.

If all you want is one small feature, this protocol is overkill. But if you're building something that runs for months, with multiple AIs working in parallel, that may one day face compliance, and whose good atoms you'd like to share with the world — what you need is a foundry like this.

This is an intro. For the actual implementation, API, police-family mechanics, and permission-model details, see github.com/eaglhuang/AI-Atomic-Framework. The framework is MIT — the whole protocol can be forked, the governance bundle swapped for your own, or used in part (just the evidence chain, or just ATMChart).
